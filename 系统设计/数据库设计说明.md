# 数据库逻辑设计说明

设计日期：2026-10-24（Asia/Shanghai）  
设计状态：关系数据模型；未建库、未生成迁移、未实现接口、未读取密钥或调用外部服务。

依据：[需求对齐记录-grill-me.md](../需求对齐记录-grill-me.md)第一部分。本文的表拆分、字段、事务边界和冲突处理是本次系统设计方案，不冒充访谈时已经确认的具体技术实现。

机器可读数据字典为[源文件/schema.json](源文件/schema.json)，共 **33 张表、42 条主要绘图关系**。每个字段的 `fk` 是完整引用；绘图关系只选主要业务外键，未把所有经办人和当前指针回引用画进主图。

## 1. 设计原则与核心决定

### 1.1 申请、内容版本与提审轮次分离

采用三个独立概念：

- `applications`：稳定申请身份，绑定学生所属班级学年与学生选定的大类入口。
- `application_revisions`：学生填写的内容、分值、材料及截图版本。未正式提交的工作版本可维护；第一次正式提交后冻结。修改已经提交的内容必须克隆新工作版本。
- `submission_rounds`：对一个确切内容版本发起的一轮审核。同一内容版本撤回后不修改也可重新提审，因此内容版本与提审轮次不能合并。

`applications.working_revision_id` 与 `applications.current_round_id` 分开保存。当前草稿可以是新版本，而当前有效的审核轮次仍引用旧版本。恢复旧已通过申请时只恢复原轮次及其计分效力，不把新草稿覆盖掉。

正式提交后的 `title`、`requested_score`、细项事实、原件关系、截图坐标和审核所见内容都不可原地修改。`content_frozen_at` 只在第一次提交时设置一次。脱敏图属于明确源摘要上的安全派生物，可以重新生成，不能借此更换审核原图。

申请的大类是学生选择的稳定入口；AI不决定该大类。本设计不隐含提供跨入口自动迁移功能。学生修改AI类别细项不受此限制。如果后续增加跨大类移动，需要显式支持新版本中的大类、重新审核及重新计算竞赛归组，不能直接修改历史申请类别。

### 1.2 状态以业务轮次为单位

轮次状态为：

| 状态 | 含义 |
| --- | --- |
| `PENDING_PEER` | 等待本班一名非本人的学生审查员 |
| `PENDING_COUNSELOR` | 初审通过，等待辅导员进一步认定 |
| `APPROVED` | 当前审核通过 |
| `REJECTED` | 人工驳回或系统奖项替代驳回，具体原因在决定/事件中 |
| `WITHDRAWN` | 学生撤回，不再占用本轮待审 |

草稿是尚未提审的工作内容，不是另一条待审核轮次。被替代属于 `REJECTED` 的特定因果来源，必须有 `award_supersessions` 与事件，不能仅用一段普通驳回备注表达。

任何状态投影更新都与不可变的 `application_events` 一起提交。审核记录绑定确切轮次与内容版本，既有实际经办人ID，也有当时姓名快照。

### 1.3 关系规范化与受限JSON

用户、角色、权限、组织关系、版本附件、识别输入及奖项替代均使用独立关系表。JSON仅承担适合整体版本化的值：

- 几何多边形和脱敏遮挡区域。
- 供应商识别原始结果、结构化错误。
- AI建议与分析输入摘要。
- 按类别定义模式的事实，例如活动次数、志愿工时、任职期限、考核、奖项层级。
- 不可变的评分规则配置及因果事件快照。

不能把用户列表、附件关系、审核决定或替代链埋进一个申请JSON。JSON字段必须有模式校验；版本号、AI基线、学生手改标记、分值、项目外键和冻结时间都是显式字段。

## 2. 表清单与职责

### 2.1 身份、组织与RBAC：11张

| 表 | 职责与关键约束 |
| --- | --- |
| `users` | 登录主体；用户名唯一；基础身份为学生/辅导员/管理员三者之一 |
| `student_profiles` | 学生专属档案；用户一对一；学号唯一且敏感 |
| `classes` | 稳定班级；不随学年复制班级名称 |
| `academic_years` | 学年选项；日期仅辅助人工核对 |
| `class_years` | 班级×学年唯一；评分版本及公示/提交事务边界 |
| `enrollments` | 学生在所选班级学年的归属；同学生同学年至多一个有效归属 |
| `roles` | 五种预置业务角色及允许的基础身份 |
| `permissions` | 角色矩阵中的权限项及硬边界说明 |
| `role_permissions` | 角色×权限唯一；矩阵布尔授权及该资源操作的最大数据范围 |
| `role_assignments` | 用户×角色×班级范围及有效期；基础角色为全局范围 |
| `counselor_classes` | 独立维护辅导员带班范围及历史 |

班长、审查员授权采用 `class_id` 范围，不把其权限授予整个系统。辅导员基础角色只说明身份，能查看哪个班还要匹配 `counselor_classes`。

`roles.scope_kind` 表示授权绑定类型（GLOBAL / CLASS），`role_permissions.data_scope` 表示该资源操作允许的最大数据范围（OWN / CLASS / LED_CLASSES / CLASS_PUBLIC / SYSTEM_METADATA），`role_assignments.class_id` 是该条具体授权所绑定的实际班级。三者不是同一个字段。先对同一条完整授权的操作、数据范围、实际班级范围和强制业务策略求交，再对允许的完整授权结果求并；禁止将角色A的操作权限搭配角色B的更大数据范围。

UML中的 `ClassYear.publicityState` 是领域读取属性，来源于一对一的 `class_publicity.is_open`；后者是当前公示开关的**唯一持久化真源**。`class_years` 只承担班级学年身份、评分版本和事务保护，不再存另一份公示状态；`publicity_events` 只保存开关历史。

未确认“一班只能一名辅导员”，因此带班关系不设置班级侧一对一。每班一名班长、至少两名不同审查员则是硬性人数约束；初始化、人员替换和撤销应在同一事务完成，不能让业务可用班级留下人数不足状态。人数约束是跨行检查，不能误认为一个普通字段CHECK即可完成。

当前关系决定当前权限；历史审核记录保存决定当时的经办人及授权，不因其后来卸任而删除。需要业务审核/原件访问时，还要叠加：

1. 基础身份允许。
2. 角色矩阵允许。
3. 本人、本班或所带班级范围匹配。
4. 当前申请/公示状态允许。
5. 初审禁止本人审核等强制约束。

管理员管理账号、班级和权限，但没有材料读取、OCR原始结果读取或业务审核权限。不能因其“系统管理”角色而默认绕过这些检查。

### 2.2 材料、OCR与AI：8张

| 表 | 职责与关键约束 |
| --- | --- |
| `file_objects` | 不可覆盖的PDF/图片原件及私有存储引用 |
| `file_pages` | 文件页、渲染版本、尺寸与坐标基准 |
| `recognition_runs` | 每页每种OCR接口的运行及结果；成功结果可复用 |
| `recognition_regions` | 文字/印章区域及来源运行 |
| `ai_analyses` | DeepSeek建议、规则版本和输入摘要，保留失败 |
| `analysis_inputs` | 一次AI分析实际使用的文件/页面/OCR关系 |
| `revision_files` | 内容版本×证明原件的多对多关系 |
| `evidence_crops` | 两类多截图、原图来源、脱敏遮挡和公示图 |

每条正式提交版本至少一个原件。一份证明包含两次活动时仍形成一个申请，通过事实和申请分值表示合计，不拆成两条活动申请。

`file_objects.sha256`可用于查重和缓存，但不是“全系统一个文件只能用于一个申请”的唯一键。全班名单可证明多名学生参加，同次活动也已允许在不同类别申报，不能因此误拦截。

图片为第0页；PDF按0起始页索引统一保存。腾讯接口对页码的约定由适配层换算。OCR和截图都引用确切 `file_pages.id`，归一化旋转、渲染尺寸或版本变化不能复用旧坐标。

`GeneralAccurateOCR`与`SealOCR`是两种独立识别运行，同页调用两者会分别记录。成功缓存键包括页面内容、接口、API/参数版本；失败可留下多个运行，不要用强制唯一键阻止真实重试。数据库运行次数不等于腾讯云主账号的真实剩余额度。

`analysis_inputs`确保“AI基于哪些材料给了这个建议”可追溯。`ai_analyses.input_revision_id`绑定开始分析时的输入修订，必须与其 `application_id` 同属一个申请；输入指纹还覆盖本次字段、材料和规则。结果到达时只保存建议，不能自动覆盖换版、已修改或已冻结的学生内容；应用建议仍核对当前工作修订、当前输入指纹和预期状态版本。UML中的 `RecognitionTask` 是页级OCR运行和修订级AI分析的概念集合，不要求将所有缓存OCR结果强行绑定单一修订。

`ai_analyses`与内容版本分别保留建议分值和学生填写分值；手动修改标记显式保存。`student_modified_score`表示本工作修订分支**曾经手动编辑计分**，改回AI原值也保持true，克隆工作修订时继承；不能用“当前申报分≠AI建议分”重新计算，也不能被迟到AI结果重置。手填兜底明确属于人工来源，没有AI建议时 `ai_analysis_id` 允许为空。

两类截图分别为：

- `VALIDITY`：如盖章、活动日期等支持文件有效性的区域。
- `PARTICIPATION`：如姓名、学号、班级等支持本人参与的区域。

各类可有多张，跨附件和页面。截图来源页必须属于本版本附件集合。公示图只能由对应源摘要生成；没有可验证的安全脱敏版时，普通同学读取路径必须拒绝回退到完整截图或原件。处理和重生成是系统设计职责，不新增学生必须填写脱敏理由或额外审批的要求。

### 2.3 规范目录、资格与计分：6张

| 表 | 职责与关键约束 |
| --- | --- |
| `activities` | 稳定规范活动ID与名称 |
| `activity_aliases` | 别名归一；同别名允许产生多个候选 |
| `activity_eligibility_versions` | 规范活动×类别×适用范围的有效/无效/移除版本 |
| `competition_projects` | 届次、赛道、组别及作品确定的竞赛项目身份 |
| `score_categories` | 七类名称、顺序及首版上限目录 |
| `score_rule_versions` | 班级学年绑定的不可变规则配置快照 |

资格范围维度直接放在 `activity_eligibility_versions`，避免另建范围表；按 `scope_key`标准化。同一活动同一范围递增 `version_no`，历史版本不覆盖。界面的删除通过新 `REMOVED`版本或活动归档表达，保留历史引用。类别采用独立维度，避免同一活动在一类获认可就自动获得所有类别资格。

本设计采用“具体范围优先，矛盾匹配不自动放行”的匹配处理：较具体且覆盖本次事实的范围优先于通用范围；若多个同样具体或不可比较的范围给出矛盾结果，不以AI相似度选一个有效结果，应明确核对活动范围或进入人工认定。这是范围冲突的设计处理，不是访谈已指定的算法。

资格范围中可选的 `academic_year_id` 只与学生选择并归档在 `enrollment` 中的学年比较；不根据活动日期或9月1日等参考日期自动推断。`effective_at` 表达某次资格认定何时生效，也不充当活动属于哪一学年的判定字段。

活动资格认定与个人审核决定分别落表。一次操作可以同时记录“活动有效”和“本人的参与材料不足而驳回”。只有活动本身无加分资格才新增 `INVALID`，个人材料驳回不能污染无效库。

正式提交时检查当前适用资格并记录采用的版本。初审结束若资格版本已经变化，设计上重新核对路由；不能以旧有效快照不加检查地直接放行。对已提交但尚未通过的冲突条目可转辅导员核定；历史已通过不因资格变无效自动撤销。

活动库按当前规范活动和范围检索受影响历史申请；不创建一套可独立漂移的“有效库表”和“无效库表”。它们是同一规范活动目录下当前认定的两种查询结果。

### 2.4 申请、审核、替代与公示：8张

| 表 | 职责与关键约束 |
| --- | --- |
| `applications` | 申请聚合根，工作版本与当前轮次双指针 |
| `application_revisions` | 学生填写内容及证据版本，提交后冻结 |
| `submission_rounds` | 每次正式提交及当前审核状态 |
| `review_decisions` | 实际审核动作、驳回原因枚举、备注与经办人 |
| `application_events` | 不可变的状态与操作因果历史 |
| `award_supersessions` | 新旧轮次替代、原状态和恢复关系 |
| `class_publicity` | 班级学年唯一当前公示开关 |
| `publicity_events` | 历次开启、关闭及开启时的待审核查 |

驳回原因使用受控枚举，不另设字典表；备注可空。正式驳回需非空原因。每轮学生初审最多一名有效经办人，但不能把整条申请设计成一生只允许一条审核记录。

`application_events.actor_type` 显式区分 USER / SYSTEM。奖项替代与恢复为系统状态事件，不创建伪造的人工 `review_decisions`；触发该原子操作的用户可在因果信息中保留。用户直接作出的审核决定仍有明确经办人。

## 3. 奖项身份、比较与恢复

### 3.1 规范活动不等于同一竞赛项目

资格复用可发生在“蓝桥杯”统一名称层面；计分去重必须细化到具体赛事、届次、赛道、组别、作品/参赛项目。

个人竞赛去重键由以下值生成：

`student_id + academic_year_id + category_id + competition_project_id`

该键在 `submission_rounds.competition_group_key`保存为派生摘要，不能由学生直接填入。原始关系仍能从外键追溯。含学年是因为系统按所选学年独立计分；含类别是因为需求允许同活动跨类别分别申报。

身份明确的项目设置唯一指纹；未知届次/作品不能全部合并为同一个“空项目”。名称相似或信息不足时先由学生确认关联，并写 `MATCH_CONFIRMED`事件。

### 3.2 当前候选与计分

比较顺序为：

1. 可得分高者优先。
2. 同分再比较奖项层级。
3. 低优先级或同优先级重复正式提交被拦截。

比较保存学生填写且本轮提交的分值及奖项事实快照，最终正确性仍由审核把关。AI不能强制覆盖学生分值。

同组最多一条 `is_current_candidate=true`轮次。新更高申请正式提交时，该新轮次立刻成为当前候选；旧项进入替代驳回并停止计分。新项待审期间该项目可能为0分，不能由计分查询偷偷退回旧通过项。

`is_current_candidate`是状态投影，不是另一个学生可编辑字段；采用条件唯一约束或等价串行事务保证唯一。单独做“先查询没有重复，再插入”不足以处理并发。

### 3.3 恢复与替代链

`award_supersessions`引用新旧提审轮次而非只引用申请ID，保存旧轮次状态、版本和造成替代驳回的事件。原来待辅导员的应恢复待辅导员，不能一律回到学生初审。

新项被驳回或撤回时，仅恢复仍然由本次替代造成的旧项状态变化：

- 原已通过，恢复其原轮次及计分资格。
- 原待审，恢复原审核阶段。
- 旧轮次后来已有独立人工决定或新有效业务，不自动覆盖，替代关系标记失效并保留说明。

A→B→C等链按轮次处理，并发事务保证任一时刻一个组只有一个当前候选。旧项恢复后还可能被另一新轮次再次替代，因此不能给 `old_round_id`设置全历史唯一。

被替代旧申请可能已经有新工作草稿；恢复原审核轮次不会覆盖 `working_revision_id`。后续是否能编辑/提交该草稿，继续受恢复后的当前审核状态、公示状态及重复检查约束。

## 4. 事务边界与幂等

| 操作 | 必须在同一原子事务内完成的内容 |
| --- | --- |
| 正式提交/重提 | 锁定班级学年边界；确认公示关闭；核对本人归属、材料、当前资格；冻结内容；建立轮次；必要时执行替代；更新当前指针及写事件 |
| 学生初审 | 检查角色范围与非本人；比较轮次状态版本；写唯一初审决定；按类别/资格路由；更新状态及写事件 |
| 辅导员审核 | 检查有效带班关系；分别保存个人决定和可选资格认定；更新申请状态及写事件；涉及失败替代恢复时同时处理旧项 |
| 学生撤回 | 校验当前轮次可撤回；写撤回事件；处理有效替代恢复；保留已冻结内容及既有审核意见 |
| 事后驳回通过项 | 写辅导员决定；使当前通过轮次停止计分；执行需要的替代恢复边界检查；公示和汇总读取立即改变 |
| 开启公示 | 锁定同一class_years记录；检查当前无待审正式申请；写公示开关及核查事件 |
| 人员替换 | 成批维护角色授权；事务结束前校验班长唯一、审查员至少两人，禁止留下业务可用班级缺员状态 |

跨新旧申请的状态事件使用同一 `operation_id`。`review_decisions.idempotency_key`防止网络重放产生重复决定；状态/版本比较保证两个审查员并发点击时只有一次有效初审。

逻辑设计不绑定具体锁实现。若以后采用SQLite，可在事务中使用适当的写入串行边界及版本校验；若采用其他关系数据库，可使用行锁或等价机制。本文没有创建任何数据库。

公示开启与新提交必须竞争同一个班级学年事务边界，而不是分别锁自己的表，否则会出现“检查无待审后，新申请插入，再开启公示”的穿透。

## 5. 实时分数、公示与导出

不设置可人工维护的 `student_total_score`真源表。建议逻辑查询分为三层：

1. **当前有效已通过条目**：只取 `applications.current_round_id`所指轮次，状态为 `APPROVED`，使用该轮次的冻结版本。竞赛另要求其为当前候选。不能把所有历史曾通过的轮次相加，也不能读新工作草稿分值。
2. **分类计分贡献**：对已通过学生申请分值执行当前班级学年的冻结规则。集体、思政等累计封顶；同竞赛项目不重复；任职取最高；志愿服务按年度最多1分的子规则处理，社会服务总类仍上限4。规则未明确部分使用审核已核定的条目分值，不擅自改回AI分值。
3. **类别合计与总分**：各类封顶为3/3/4/10/6/4/5，基准70、扣分0、理论最高105。

每条最终分值及汇总使用十进制两位小数、四舍五入。申请分值是审核对象，分类封顶后的实际计分贡献可能更低，界面和导出应区分二者，不能修改原申请分值来凑封顶。

公示和Excel必须使用同一组计分查询：

- 公示开放时普通同学仅查看本班已通过条目、类别合计、总分、脱敏关键截图和学生审查员姓名。
- 完整原件及完整截图的授权不由公示开关放开。
- 学号字段和截图中的学号均须遮挡。
- 辅导员公示期间驳回通过项后，查询即反映新分数；公示不是历史冻结快照。
- Excel保留既定15列、基准70、扣分0及空签字；类别项目明细与最终封顶合计分别表达。
- 如以后增加缓存，缓存只能是可重建投影，并在提交/审核/替代/恢复后同步失效或更新；不得成为另一个可改总分来源。

待审检查针对**当前业务轮次**，不是全历史表。已撤回轮次、被替代旧轮次、旧驳回轮次和未提审草稿不阻挡；恢复成待审的原轮次则重新参与检查。

## 6. 类型、外键与通用审计约定

### 6.1 逻辑类型

- 所有表主键统一 `UUID`，具体数据库可选对应原生类型或受约束字符串。
- 分值使用逻辑 `DECIMAL(6,2)`，置信度使用定标十进制。
- 若后续选择SQLite，推荐把所有两位小数分值以**整数百分位**保存，例如0.38→38、70.00→7000，服务层使用十进制 `ROUND_HALF_UP`；不依赖SQLite动态类型或二进制浮点来保证金额式精度。
- 时间记录明确使用统一时间基准，展示按Asia/Shanghai；所选学年不从活动日期自动推导。
- `ENUM`表示受控取值，后续可用CHECK或应用枚举实现。

### 6.2 外键与回指

`schema.json`字段级FK覆盖真实逻辑引用；关系图省略以下常见线以减少交叉：

- `created_by`、`changed_by`、`maintained_by`等审计用户。
- `applications.working_revision_id/current_round_id`回指。
- `submission_rounds.last_event_id`及替代事件回指。
- OCR来源、规则来源和资格来源等辅助关系。

回指初建时允许为空，相关内容/轮次建立后在同一事务更新。不能因此放弃“当前指针必须属于本申请”的复合完整性校验。循环外键的实际DDL顺序、延迟约束或等价校验留待实现阶段处理。

UML里的 `ApplicationRevision.categoryCode` 是本申请稳定填报入口的读取映射，物理字段位于 `applications.category_id`；`CompetitionProject` 不持久化一个排他类别，个人去重键才包含申请类别。图中概念字段不得成为禁止同活动跨类别申报的隐含约束。

业务历史外键默认限制物理删除，不使用级联删除把申请、文件和审核历史一并清空。字典和关系采用归档/失效。

### 6.3 审计继承

数据字典列出的关键审计字段之外，实现可统一增加：

- 可维护配置/关系：`created_at`、`updated_at`、`created_by`、`updated_by`与并发版本。
- 不可变内容/决定/事件：创建者与创建时间，不提供普通更新或物理删除入口。
- 派生识别/渲染任务：输入摘要、处理版本、状态及错误码。

这些字段是审计元数据，不能代替审核决定或状态事件。实际API密钥、令牌、带凭据的签名URL不存入这些表；本设计没有读取 `secrets`。

## 7. 需要保留的设计边界

- 学生自由改分与确定性汇总分层；数据库不设置“必须等于AI分值”的约束，不增加修改理由必填。
- 评分规则版本化用于可追溯，首版不新增在线改规则或回算历史成绩功能。
- 同一活动跨类别可申报，去重键必须含类别；不能把赛事规范名称当全部历史年度唯一项目。
- 学号脱敏是输出权限的一部分，不能只隐藏列表学号而公开原始参与证明。
- 公示只有提交锁，没有成绩冻结；辅导员事后驳回继续生效。
- 范围冲突、审核期间资格改变、替代链并发等处理是本次设计决定，具体实现必须通过一致性验证；不得把它们表述成额外的用户访谈原答。
- 本文只交付数据模型及设计说明。真实数据库、迁移、样本接口调用、OCR额度消耗、服务启动与部署均未执行。
