采用模块化单体的逻辑边界。当前不锁定 Web 框架、数据库产品和部署方式，不将参考项目技术栈误记为已确认要求。

## 3. RBAC 设计

### 3.1 授权模型

1. `User.baseIdentity` 为 STUDENT／COUNSELOR／ADMIN 之一，作为不可通过权限矩阵绕过的基础身份约束。
2. `Role` 定义五类既定业务角色及其允许的基础身份、授权绑定类型 `scopeKind`。
3. `RolePermission` 是“资源×操作”矩阵，记录允许状态及该操作最大数据域 `dataScope`。
4. `RoleAssignment` 记录用户获得的角色、实际班级范围、授予人和有效期。
5. `CounselorClassAssignment` 定义辅导员的所带班级；`Enrollment` 提供本人学年班级归属。
6. 逐条授权计算“操作允许 ∩ 最大数据域 ∩ 实际班级关系 ∩ 对象规则”，再对合法授权求并集。

数据域包括 OWN、CLASS、LED_CLASSES、CLASS_PUBLIC、SYSTEM_METADATA。角色的 GLOBAL／CLASS 绑定类型不等同于读全部业务数据。不得把一项角色的操作权限与另一项角色的范围拼接成越权。

### 3.2 强制策略

- 学生、辅导员、管理员基础身份互斥；班长和审查员仅可授予相应班级学生，且可叠加。
- 每班一个现任班长、至少两名不同学生审查员；兼任班长与审查员仍只算一人。
- 审查员不得审核本人；一轮只需要一个有效学生审查决定。
- 管理员无证明材料读取和业务审批权限。
- 公示期间禁止正式提交、重提、奖项替代；辅导员事后驳回仍允许。
- 普通同学只读已通过公示投影，名单与截图都遮挡学号，不提供原件地址。
- 原件每次读取都按对象授权；截图的公开变体与审核完整版本分离引用。

完整角色权限矩阵见《RBAC与领域设计说明.md》。

## 4. 为什么区分申请、版本和轮次

- `Application` 是稳定业务身份，关联本人、班级学年和填报入口，分别保存 `working_revision_id` 与 `current_round_id`。
- `ApplicationRevision` 保存内容、学生申报分值、AI 来源和材料／截图集合；提交后内容冻结，后续修改克隆工作版本。
- `SubmissionRound` 保存某一确切版本的提审轮次、阶段、状态和乐观版本号。同一内容也可能撤回后重新提审，因此轮次不能等同于内容版本。
- `ReviewDecision` 绑定轮次与版本、经办人及对应授权；系统自动替代不伪造人工审核决定。
- `ApplicationEvent` 记录 USER／SYSTEM 及状态前后、因果关联；`AwardSupersession` 保存两端轮次、旧状态与恢复守卫。

因此，旧省赛申请被替代后即使学生已经编辑新草稿，后来国赛失败时，仍能恢复旧的已审核轮次，而不把新草稿当作通过内容。A→B→C 替代链按轮次与事件追踪，不靠单个 previousApplicationId 字段猜测。

## 5. 关键状态与事务

| 操作 | 检查与结果 |
| --- | --- |
| 保存草稿 | 仅本人；可在公示期进行；AI 迟到结果不得覆盖较新的人工编辑 |
| 正式提交 | 校验班级／学年、权限、材料、无效活动、当前公示状态、同项目优先级；冻结内容、建立待学生审核轮次 |
| 高分替代 | 在正式提交事务中，旧较低优先级轮次立即系统驳回并停止计分；新项待审不计分；记录替代前状态和因果事件 |
| 学生审查 | 非本人、本班、状态版本一致；四类直接通过，另三类按活动资格决定直接通过或待辅导员 |
| 辅导员审核 | 所带班级；活动资格认定与个人材料决定分开记录；材料有误不能自动把整个活动标无效 |
| 撤回／驳回新高分 | 仅回退本次替代造成的旧项状态；原通过恢复计分，原待审恢复原阶段；不得覆盖后来独立人工决定 |
| 公示开启 | 与提交共用班级学年并发边界，当前不存在待学生／辅导员审核轮次时开启；草稿不阻挡 |
| 公示期间纠错 | 辅导员可驳回已通过项，成绩实时更新；不会因纠错自动冻结或关闭公示 |
| 审查员替换 | 同一事务完成任免并检查最终至少两名不同学生，保留旧授权和审核历史 |

设计状态为草稿／待学生审核／待辅导员审核／通过／驳回／撤回等。草稿内容状态与审核轮次状态分别表达；系统替代通过“驳回状态＋替代原因／事件”对用户呈现。具体枚举、状态前置条件见数据库与 RBAC 说明。

若公示开启后，辅导员驳回新高奖触发旧待审项恢复，公示仍只展示通过项；开启门槛不是持续成绩冻结条件，不新增“自动关闭公示”。

## 6. 数据库与证据来源链

- 33 张表是逻辑设计，尚未执行建表或迁移。完整字段、PK／FK、可空性及约束见《数据字典.md》和 `源文件/schema.json`。
- 金额／分值逻辑类型为 DECIMAL(6,2)；后续若选择 SQLite，建议以整数百分位存储，避免二进制浮点计分；此处不是数据库产品已定。
- 文件内容摘要用于识别复用和完整性，不做“全系统一份文件只能属于一个申请”的错误唯一约束。
- “同文件多次活动不拆条”是申请聚合粒度，不阻止同班名单被不同学生合法使用，也不阻止满足不同类别的合法申报。
- 截图引用确切文件页、渲染版本及坐标，且源文件必须属于该内容版本的附件集合。
- 公示脱敏图保存原截图指纹／变体版本，新截图不能继续使用旧脱敏变体；只在确认对应安全版本时供公示读取。
- 活动采用稳定规范 ID、别名和不可变资格认定版本；界面删除采用移除／失效状态，保留历史引用。
- 具体竞赛项目按届次、赛道／组别及作品区分，与可跨届复用的活动资格身份分开。
- 最终总分不是可编辑真源，由当前有效已通过轮次按规则派生，公示和 Excel 共用同一计算服务。
- 成绩查询以班级学年成员为主、关联其已通过条目；没有申报的同学仍保留70分基准，不能仅查询有加分申请的学生。

ER 图展示42条主要关系以保持可读；字段字典保留包括审核人、创建人等全部外键。少画辅助外键不等于取消数据库完整性要求。

## 7. 本版提出、请在设计确认时一并审阅的细节

这些是对已确认需求的设计细化，不是新增访谈结论：

1. **资格范围重叠**：更具体的适用范围优先；同等具体度出现矛盾认定时不自动放行，交辅导员处理。避免通用有效和某届无效同时匹配时由 AI 随机选择。
2. **大类入口归档**：当前将七类入口存于稳定申请，细项和分值可随内容版本修改。需要改大类时建议在正确入口重新填报，原项按既有撤回／驳回流程处理；如希望直接在原申请换大类，需要调整版本中的类别快照设计。
3. **学年班级档案**：学生只选择学年、不自行选择班级；按管理员绑定的班级建立／复用学年归属，保留历史班级记录，不按活动日期硬判断学年。
4. **并发恢复守卫**：自动恢复检查替代事件仍是造成当前状态的原因；之后独立人工驳回优先保留，不因新项撤回而被抹去。
