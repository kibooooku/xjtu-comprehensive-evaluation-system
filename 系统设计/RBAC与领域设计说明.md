# RBAC 与领域设计说明

> 设计依据：项目《需求对齐记录-grill-me.md》第一部分及 Q1—Q33 最终确认结论。本文为待用户确认的设计稿，未创建应用、数据库或接口调用程序。

## 1. 设计方案与取舍

| 决策 | 采用方案 | 比较过的替代方案与原因 |
| --- | --- | --- |
| 身份与学生附加职责 | User.baseIdentity 保存互斥基础身份；RoleAssignment 赋予学生的班长、审查员职责 | 不采用班长、审查员互斥子类继承，因为同一学生可以兼任两者 |
| 角色与数据范围 | RBAC 的角色—权限矩阵，加带班级作用域的角色授权、带班关系和资源条件 | 不采用“有审批权限即可全局访问”的纯全局 RBAC，无法满足班级隔离；不采用纯条件授权替代 RBAC，否则失去用户明确要求的角色权限矩阵 |
| 申请与审查历史 | Application 稳定标识、ApplicationRevision 内容修订、SubmissionRound 各次提审状态 | 不把申请内容和当前审核结果覆盖写入同一条记录，避免驳回重提后无法还原已审核材料 |
| 自动替代与人工审核 | AwardSupersession 与 StateEvent 表达系统替代和恢复；ReviewDecision 表达人工决定 | 不把系统驳回伪装成审查员决定；不等新项批准后才替代，因为用户确认在正式提交时立即替代 |
| 总分存储 | ScoreSummary 是由当前已通过轮次派生的值对象；导出、公示复用同一计分服务 | 不把学生可编辑条目分值扩展为可直接修改最终总分；不把导出样表中的手填总分当算法 |
| 公示一致性 | ClassYear 是共同并发边界；ClassPublicity 保存唯一当前开关，PublicityEvent 追加开关历史 | 不采用只在前端隐藏按钮的锁定方式；不把公示做成冻结快照，因为辅导员公示期间仍可驳回并更新分数 |

## 2. 核心模型

### 2.1 身份与 RBAC

基础身份只允许 STUDENT、COUNSELOR、ADMIN 三者之一。学生档案、学生学年班级归属与 RBAC 角色分别建模：身份说明用户是谁，RolePermission 说明角色能做什么，RoleAssignment 与带班关系说明在哪个范围执行。

- Role：五种预设业务角色，学生、班长、学生审查员、辅导员、系统管理员。
- Permission：按资源与操作定义权限，例如 application.read、review.peer_decide、publicity.manage。
- RolePermission：角色×操作矩阵项，保存 isAllowed 及最大访问域 dataScope；取值 OWN、CLASS、LED_CLASSES、CLASS_PUBLIC、SYSTEM_METADATA。
- RoleAssignment：用户的角色赋予记录；班长、审查员角色带 classId、生效和撤销时间；基础身份角色须与 baseIdentity 一致。
- CounselorClassAssignment：辅导员实际带班关系，独立于全局角色定义。
- Enrollment：学生在所选学年的班级归属，不按活动日期硬编码9月1日边界。
- ClassYear：班级与学年组合，作为申请、公示、统计范围及并发控制的共同对象。

权限并集只在完整授权之间求并集。一次允许必须同时满足该角色的资源操作、该条角色赋予的数据范围以及强制策略；不能用角色 A 的操作权限搭配角色 B 的更大范围。

Role.scopeKind 的 GLOBAL／CLASS 只说明角色授权的绑定类型，不表示角色能读取全系统业务数据。RolePermission.dataScope 是对应资源操作的最大范围，再与 RoleAssignment.classId 或 Enrollment／CounselorClassAssignment 解析的实际范围相交，最后施加对象状态和身份硬约束。OWN 为本人，CLASS 为授权班级，LED_CLASSES 为所带班级，CLASS_PUBLIC 为本班开放公示的已通过脱敏内容；SYSTEM_METADATA 为账号、组织、权限或活动目录等元数据，不能扩展为原件、OCR原始材料或业务审核的全局权限。

ClassYear 的 /publicityState 是 UML 派生属性，由唯一 ClassPublicity.isOpen 读取，物理表 class_years 不再保存另一个开关。class_years.lock_version 只承担共同事务边界；class_publicity.lock_version 用于其当前状态版本。历史开关保存在 publicity_events，而不是创建一套可独立漂移的公示周期状态。

### 2.2 申请、修订和提审轮次

Application 保存 enrollmentId、categoryId、workingRevisionId、currentRoundId 等稳定关系，不独立维护另一套可冲突的审核状态。学生及班级学年由 Enrollment 关联取得，显示状态由当前 SubmissionRound 推导。categoryId 是学生选定的稳定大类入口；内容修订只保存细项、分值和事实，本设计不额外提供跨大类迁移。

ApplicationRevision 保存标题、申报分、手动改分标记、规范活动及具体参赛项目绑定。其展示的大类由稳定 Application 派生，不保存第二个可冲突的大类字段。工作稿可编辑；正式提交时冻结，后续修改创建新的工作修订，不覆盖已提交内容。工作稿指针可为空，提审指针与工作稿指针分别管理。

SubmissionRound 保存本次提审绑定的冻结修订、轮次号、状态、状态版本和提交时间。ReviewDecision 的 revisionId 必须等于 round.revisionId。StateEvent 对应 application_events，直接记录相关修订；工作稿事件的 roundId 可以为空，提审状态事件必须与对应轮次修订一致。AwardSupersession 物理引用新旧 roundId，UML 中两端 revisionId 从对应轮次派生，不再存冗余版本指针。以上防止材料版本与审核对象错位。

建议轮次状态包含 PENDING_PEER、PENDING_COUNSELOR、APPROVED、REJECTED、WITHDRAWN；自动替代的驳回通过事件原因区分。草稿属于工作修订，不用增加“草稿提审轮次”。这些状态名称是设计表达，不改变已确认业务行为。

附件和截图属于内容修订。正式提交至少一个原件；同文件内多次活动合并一个条目。EvidenceCrop 引用确切的 file_pages.id，文件、页索引、渲染版本、尺寸和坐标基准均由该页取得；源文件必须属于同一修订的附件集合。另保存证据类别、裁剪多边形、完整截图摘要及公示脱敏版本。仅在 public_asset_status=READY 且源摘要和处理版本匹配时提供公示图，失败不能回退原图。有效性证明、参与证明都允许多张。

RecognitionTask 是识别任务的领域聚合投影，不新增同名持久化表：OCR 对应 recognition_runs，绑定 file_pages 页面并可被多个内容版本复用；DeepSeek 对应 ai_analyses，内容版本通过 ai_analysis_id 引用其建议基线。输入指纹和实际分析输入避免迟到结果覆盖学生修改。AI 原始建议、学生最终申报分、系统汇总贡献值分开保存或派生，学生手动改分无需理由。

ActivityQualification 对应 activity_eligibility_versions，按规范活动＋类别＋标准化范围键递增版本，范围可限定学年、届次、赛道和组别，保留 effectiveAt 和认定人。decision 取 VALID、INVALID、REMOVED；REMOVED 是移除该范围认定，不等于活动无效。界面有效库、无效库是当前版本查询，不另存两套资格真源。具体范围优先、矛盾结果转人工属于本次设计选择。

CompetitionProject 保存赛事、届次、赛道、组别、作品的身份，类别不重复存于项目表。个人去重组由学生＋所选学年＋申请类别＋具体项目派生，保证同活动跨类别申报不被错误互斥。ScoreRule 是班级学年所绑定 score_rule_versions 中按类别解析的策略，不新增规则真源；实际计算使用 ClassYear.scoreRuleVersionId。

## 4. 不可绕过的业务策略

1. 学生、辅导员、管理员基础身份互斥；班长、审查员只授予对应班级的学生，允许同人兼任。
2. 每班一名现任班长，至少两名不同的有效审查员；重复授权或同人兼任不能重复计数。角色任免保存时在同一事务内检查下限，演示数据初始化满足完整配置。
3. 一条申请的一轮初审只需一位非本人审查员完成，共享队列不等于双人复审。多人竞争审批时只能有一个基于当前状态的有效决定。
4. 类别由学生选定；固定七类、至少一个原件、班级学年归属和所选活动资格在正式提交时校验。无效活动仅拦正式提交，草稿和误匹配纠正仍可用。
5. 学生自由修改 AI 内容与申报分，无理由要求。审核端展示手动修改计分标记；封顶、去重、取最高由计分服务执行。
6. 科研、文体、奖励三类的未知资格进入辅导员；已知有效且范围匹配可在学生审查员批准后直接通过。其他四类学生初审通过即通过。
7. 个人材料或分值错误只驳回本次申请，不能由此把整个活动加入无效库。
8. 同一具体竞赛项目按学生、赛事届次、赛道／组别及作品区分；高分优先，同分比较奖项层级。资格复用的活动名称与具体项目去重键是两个层次。
9. 更高优先级申请正式提交即自动驳回旧项，包括已通过项；新项待审期间不计分。后续失败只恢复相应替代影响，不覆盖独立人工决定。
10. 开启公示前没有当前待审正式轮次；草稿、撤回工作稿和历史状态不误计为当前待审。
11. 公示期间禁止新正式提交、修改重提和奖项替代，允许保存草稿；辅导员仍可驳回已通过项并更新公示分数。
12. 普通同学只看到已通过条目和脱敏截图，不给原文件；原件和审核完整证据按角色与班级逐次鉴权，不能只保护菜单。
13. 学年由学生选择，时间归属人工核查；公示时长提示至少三工作日，由辅导员掌握，均不擅自增加日期硬拦截。
14. 本项目采用 DeepSeek 与腾讯高精度 OCR／印章识别；腾讯仅免费额度。凭据留在后端本地配置，不进领域表、图稿、浏览器或日志；本设计未读取或调用凭据。

## 5. 关键事务与一致性边界

### 5.1 审查员任免

锁定班级当前角色配置，校验操作者是本班班长、目标均为本班学生、现任班长唯一以及操作后的不同审查员人数至少两人，再统一保存授权和任免审计。替换不能先撤后补造成中间可见的不足两人状态。

### 5.2 正式提交及奖项替代

在 ClassYear 同一并发边界下检查公示未开启、当前申请可提交、附件完整、最终活动不在无效库。冻结工作修订，创建 SubmissionRound，并校验同项目优先级。存在更低优先级有效旧轮次时，原子保存 AwardSupersession、旧项系统驳回事件和新轮次；不能新项提交失败却已取消旧项。

同分比较层级，较低或同级重复正式提交被拦截；歧义项目关联须先由学生确认。系统操作写 StateEvent，保留旧轮次原审核人与人工历史。

### 5.3 审核决定

核对当前 roundId、revisionId 与 stateVersion，执行非本人、角色、数据范围和阶段约束；新增 ReviewDecision 和 StateEvent，按类别及活动资格决定直接通过或进入辅导员。对同一状态版本的并发操作仅允许一个生效。

辅导员的活动资格认定与个人审核分别表达，可出现“活动有效但个人材料不足”的组合，避免污染公共活动库。

### 5.4 失败恢复

新轮次被驳回或撤回时，依据仍有效的 AwardSupersession，验证旧轮次仍处于由此替代造成的状态，恢复 oldState 并追加系统事件。oldLockVersion 明确保存替代前旧版本；恢复守卫通过 supersededEventId 与旧轮次当前 lastEventId、状态及事件快照确认因果一致，不能误把替代前版本当作当前应匹配版本，也不虚设一个数据库没有的替代后版本字段。

恢复不覆盖已有工作稿或历史修订。若恢复为待审，该轮次重新进入共享审核队列；若恢复为已通过，恢复对应计分。设计不新增“恢复后自动关闭公示”规则。

### 5.5 开启公示

与提交共用 ClassYear 并发保护，在同一一致视图中确认当前待审数为零，再设置唯一 ClassPublicity 当前开关并追加 PublicityEvent。通过或驳回均属已审结束，草稿不阻挡。关闭公示恢复提交；下一次开启重新检查。

公示只是开启门槛和提交限制，不是成绩冻结。辅导员公示期间撤回已通过项后，ScoreSummary 和公示清单由当前状态重新派生。

### 5.6 计分与导出

ScoringService 读取当前已通过轮次对应的冻结内容，执行70基准、七类上限3／3／4／10／6／4／5、同项目及任职取最高、学年志愿工时规则和两位小数。公示、学生查询和15列导出使用同一口径。

同一文件的两次广场舞保留一个0.6条目，不生成两个申请。导出扣分列0、签字空；不使用示例表中手填合计作为规则。

## 6. UML 与数据模型对应

- 第一张图：身份、组织、Role—Permission—RoleAssignment 及授权服务；没有把班长或审查员画成互斥学生子类。
- 第二张图：Application → ApplicationRevision／SubmissionRound → 人工审核与系统事件；证据引用确切渲染页，识别任务为已有OCR／AI记录的领域投影，奖项替代连接新旧轮次并派生其修订。
- 第三张图：规范活动和别名、按类别及范围版本化的资格、具体竞赛项目、规则、公示唯一当前开关与派生分数；开关历史由 publicity_events 保存。
- 图中的服务、policy、value object 不是都需要独立数据库表。ScoreSummary 是派生对象；类图不应强迫数据库存储可手工篡改的最终总分。
- 具体物理字段、外键、唯一约束与索引以统一 ER 和数据库设计稿为准；UML 允许只展示理解关系必需的字段，不等于完整字段字典。
