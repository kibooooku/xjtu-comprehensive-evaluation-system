# 当前版本 UML 核对说明

日期：2026-10-26。依据当前实现 `2e3abc3` 及[现行申报合同](../docs/申报简化与活动匹配.md)更新，替代初始设计中已经改变的业务类关系。本次只更新 UML 与 ER，不再制作数据流图。

## 建模口径

本项目使用 FastAPI、SQLAlchemy Core 和 SQLite，主要业务由模块函数实现。图中的 `entity` 是数据库表的领域类视图，`service` 是现有模块/函数的责任分组，`reference` 表示在其它图中展开的对象；`JobWorker` 同时对应实际 Python 类。图中的服务名称不表示新增了一套 ORM 类或新业务功能。类型为领域逻辑类型，物理字段、全部外键和索引以当前 ER 为准。

语义源文件为[uml-model.json](源文件/当前版本/uml-model.json)，包含类、属性、操作、关系种类、多重性、代码映射及约束注释。组合关系表达领域生命周期，依赖虚线表达服务调用或逻辑引用，不将这些依赖当作物理外键。

## 相对初始设计的主要变化

1. **RBAC 保持独立授权。** 用户只有一种基础身份；班长、审查员通过角色授权叠加，辅导员通过带班关系取得范围。每条授权先与数据域、班级关系、强制规则求交，再合并合法结果；不采用学生、班长、审查员的继承树。
2. **申报改为大类容器和小项。** 同学生学年归属、同大类只有一份 `CategorySubmission`，通过 `CategoryItem` 一一关联小项 `Application`。审批状态属于小项的轮次，容器没有独立批准状态。小项通过后仍可向容器增补新项。
3. **内容版本和审批轮次分开。** `ApplicationRevision` 保存名称、申报分值、备注及扩展事实，提交即冻结；`SubmissionRound` 引用确切版本，决定、事件记录人工审批。单项和批量直接提交，保留版本冲突与部分成功处理。
4. **活动匹配和资格统一。** 只有科研、文体竞赛、任职显示自由填写的获奖/评定等级及可搜索的已认定活动。AI 从全库检索的合法候选匹配；搜索、详情、提交、审批共用活动/大类/学年的判定，历史具体范围冲突交辅导员。其它四类只显示名称、分值和备注。
5. **竞赛重复改由人工复核。** 当前小项不再自动关联、替代、驳回或恢复另一项。`competition_projects`、`award_supersessions` 等仅作历史兼容，在完整 ER 标识，当前业务 UML 不再画成活跃的替代服务。
6. **评分和公示共用派生结果。** 科研、文体按已通过分值累加并封顶，任职取最高，志愿年度子项封顶 1 分；基准 70。公示前全部正式小项审结，公示期间暂停提交，可靠脱敏后才提供公示证据。Excel 与成绩页使用同一查询计算，不另建可编辑成绩真源。
7. **材料处理升级为持久双队列。** 确认上传后先检测文字层，必要时云 OCR；取得可用文字后自动衔接 AI。每用户最多同时识别 3 个文件、分析 3 个小项，两类队列独立；服务端已入队任务不随页面切换或刷新取消。尚未上传完的浏览器本地文件与服务端持久任务分开。
8. **证据和并发保护显式入图。** 原件、页、识别运行、文字区域、分析输入、证据截图可追溯。参与身份与本人奖次/考评最多两张图；有效性只截活动名称、时间、印章。输入指纹、任务所有权、文件租约、成功缓存和原子额度预留共同保护任务及人工稿。
9. **系统设置包含逻辑引用与汇总归档。** 当前学年、OCR 调用次数归档保存在 `system_settings.value_json`；AI 依赖任务、活跃文件租约保存在任务 `result_json`。这些 JSON 引用不是新增物理外键或独立表。归档次数保留云调用保护，不保存已清理账户的个人 OCR 文本。
